# 스마트홈 실기기 기반 개선 계획

_2026-09-26 기준. 실제 Home Assistant의 SwitchBot 패널을 중심으로 구축 범위와 도입 순서를 정한다._

> [!abstract] 판단
> **에어컨의 ON/OFF는 확정 전원 명령이 아니다.** 사용자 확인에 따르면 전원 토글과 모드/예약 순환이다. 우선 이 실제 기능을 정확히 표시하고, 커튼·환경 알림부터 개선한다. HX-light 조명의 HA 직접 연결과 프로젝터의 네트워크 전원 제어는 호환성 시험 후 결정한다.

Amazon 두 링크의 본문을 직접 확보하지 못했다. 검색에 표시되는 상품명·Android 버전·밝기 광고를 실제 보유 제품의 확정 사양으로 채택하지 않는다. 본체 라벨, 구입 당시 설명서, 기기 설정 화면이 다음 확인 근거다.

이번 조사에는 인증된 HA 상태·대시보드·리소스 목록이 제공되지 않았다. 실제 클릭, IR 송신, 페어링, HA 재시작, GitHub 수정은 수행하지 않았다. 이 문서는 구현 타당성 판단과 후속 감사의 실행 계획이다.

## 🎯 2. 설계 원칙: 실제 기능에서 시작하기

1. HA에서 작동하는 패널의 entity와 action을 먼저 찾는다. 패널의 화면 모양을 복제하는 것이 목적은 아니다.
2. 버튼 하나마다 실제 호출 대상과 물리 결과를 연결한다. 아직 연결되지 않은 버튼은 운영 화면에 표시하지 않는다.
3. 제어 가능성과 상태 확인 가능성을 별도로 기록한다. IR 리모컨의 ‘켜짐’ 표시는 실제 전원 피드백이 아닐 수 있다.[^switchbot]
4. 새 스크립트는 검증된 action을 재사용하는 짧은 조합으로만 만든다. 이름부터 만들고 IR 버튼이 존재한다고 가정하지 않는다.
5. 자동화에 넣을 수 없는 토글·순환 버튼도 수동 리모컨으로는 유용하다. 의미를 정확히 표시한다.
6. HA를 일상 자동화의 주 계층으로 두고 SwitchBot 앱과 SmartThings를 보조 경로로 유지한다.
7. 계정 키, 실제 device ID, HA 저장소 원본은 공개 Git에 넣지 않는다.

| 구분 | 예 | 운영 화면의 표현 |
| --- | --- | --- |
| 실측/기기 피드백 | 커튼 위치, CO₂ 측정 | 값과 마지막 수신 시각 |
| 명령 이력 | IR 에어컨 마지막 버튼 입력 | ‘마지막 요청: 모드 다음 단계’ |
| 토글/순환 | 선풍기 전원, 풍량 변경 | ‘전원 버튼 1회’, ‘풍량 다음 단계’ |
| 미검증 | HX-light 밝기 직접 제어 | ‘연동 확인 대기’, 실행 버튼 숨김 |

## 🔍 4. 실제 패널 인벤토리와 저장소 정정

### 사용자 확인된 버튼 계약 — 2026-09-26

패널 이름과 실제 기능은 다르다. 아래 표는 사용자 답변을 의미별로 정리한 것이다. 이 이름을 실제 entity ID로 추정해 코드에 쓰지 않는다.

| 실제 패널 | 누르는 버튼 | 실제 동작 | 새 표시 이름 제안 |
| --- | --- | --- | --- |
| 전동커튼 3E | 기존 커튼 조작 | SwitchBot 커튼의 현재 기능 | 전동커튼 3E 유지 |
| 에어컨 수동 | ON 또는 OFF | 둘 다 전원 버튼을 1회 누르는 토글 | 에어컨 전원 버튼 1회 |
| 에어컨 off 모드 변경 / on 1시간 切 | ON | 자동 → 제습 → 냉방 → 난방 → 송풍 → 자동 | 에어컨 모드 다음 단계 |
| 에어컨 off 모드 변경 / on 1시간 切 | OFF | 종료 예약 1시간 → 2시간 → … → 9시간 → 예약 없음 | 종료 예약 다음 단계 |

두 번째 패널은 이름의 on/off 문구보다 **사용자가 확인한 ON=모드 변경, OFF=종료 예약**을 우선한다. HA에서 실제 요청을 확인해 이 대응을 검증한다.

권고 대시보드는 에어컨에 위 세 개의 수동 버튼만 둔다. ‘끄기’, ‘냉방’, ‘예약 취소’처럼 확정 동작으로 표시하지 않는다. 현재 모드·예약 단계가 물리 리모컨이나 누락된 IR 때문에 달라질 수 있어, 버튼 누름 횟수만으로 확정 상태를 복원하지 않는다.

기존 `aircon_off`가 이 전원 토글 패널의 turnOff에 매핑되면 꺼진 에어컨을 켤 수 있다. 다른 패널에 매핑되면 예약을 변경할 수도 있다. **실제 device 매핑은 미확인**이므로 현행 라이브 결함으로 확정하지 않되, 외출·환기·수면·음성에서 해당 스크립트의 자동 실행은 구현 검토의 최우선 제외 대상이다. 이번 문서 작업은 활성 자동화를 직접 변경하지 않았다.

기존 냉방26·난방20·제습·OFF는 앞으로 확보할 수 있는 프리셋의 허용 범위일 뿐, 현재 사용 가능한 기능이 아니다. 원래 리모컨이 완전 상태 코드를 송신하고 Hub에서 성공적으로 재생할 수 있는지 확인해 프리셋 확보 가능성을 판단한다. 온도 버튼을 학습하지 않고 모드 순환 횟수만으로 ‘냉방26’을 만들 수 없다. 확보가 안 되면 수동 리모컨 수준을 구축 상한으로 받아들인다.

### 실제 HA에서 확보할 최소 자료

사용자가 로그인한 HA에서 설정 → 기기 및 서비스 → SwitchBot 관련 통합과 현재 대시보드를 읽기 전용으로 확인한다. 패널이 기본 카드인지, 사용자 카드인지, 외부 웹 패널인지 먼저 구분한다.

| 항목 | 기록 내용 |
| --- | --- |
| 표시 이름/통합 | 사용자가 쓰는 기기 이름, SwitchBot Cloud/Bluetooth/기타 구분 |
| entity 또는 action | 실제 존재하는 연결 대상과 지원 기능 |
| 호출 의미 | 확정 ON/OFF, 토글, 다음 단계, 절대값 지정 |
| 상태 출처 | 기기 보고, HA 추정, 알 수 없음 |
| 접근성 | S23 화면에서 접근 경로, 중복 버튼, unavailable 표시 |
| 검증 증거 | 실제 동작 횟수, 응답 지연, 물리 리모컨 사용 후 차이 |

운영 entity 매핑은 로컬/HA에 보관한다. Git에는 익명화한 기능 계약과 placeholder만 저장한다. 기존 세션 토큰을 브라우저 저장소에서 추출하지 않는다.

### 09-22 PKM과 09-26 소스의 차이

GitHub main의 package에는 선풍기 `fan_power`, `fan_speed_cycle`, `fan_timer_cycle`, `fan_mute_toggle`가 있다. 기존 PKM의 약풍·중풍·강풍 직접 지정과 2시간 설정은 현행 코드 설명으로 재사용하면 안 된다.[^repo]

현재 로컬 configuration 예시의 allowlist는 15개다. 이전의 18/18 검증은 과거 revision의 결과다. 이번 계획에 따라 구현할 때는 숫자를 고정하지 말고 현재 정의와 호출을 다시 대조한다.

대시보드의 여섯 장면은 `tap_action: toggle`을 사용하고 있다. 향후 실행 버튼은 검증된 script를 1회 시작하는 방식으로 검토하고, 실행 중 재누름·실패·중복 요청을 시험한다. **소스상 검토 대상**이며 현재 라이브 오동작이 재현됐다는 뜻은 아니다.

일상 화면에서는 entity 연결 설정, 프로젝터 분리 코드 옵션 같은 관리용 helper를 별도 설정 화면으로 옮긴다. 기존 사용자 설정을 삭제하거나 임의로 다시 만들지는 않는다.

## 💡 5. HX-light 조명 도입 판단

대상: [조명 구입 링크](https://www.amazon.co.jp/dp/B0F4L3B2VM).

공식 Google Play의 Hxlight(`com.dxc.delight`) 설명은 Bluetooth/RF 무선 조명 제어를 명시한다. 사용 중인 앱과 패키지가 같은지 먼저 확인한다. 이 설명만으로 조명 리모컨도 IR이라고 판정할 수 없다.[^hxlight]

SwitchBot Hub Mini의 가전 리모컨 학습은 IR 방식이다. RF/Bluetooth 리모컨은 그 기능으로 복제할 수 없다.[^hub]

### 우선 확인 순서

1. 조명 본체·전구·리모컨 모델과 앱의 스토어 링크를 기록한다.
2. 앱 이름은 사용자 답변으로 Hxlight 확인 완료. 리모컨 설명서에서 IR, RF, 2.4GHz, Bluetooth 표기를 확인한다.
3. 카메라 발광 확인과 시야 차단 시험은 보조 증거로만 쓴다. 카메라에서 빛이 안 보인다는 사실만으로 RF 확정은 하지 않는다.
4. IR이 확인되면 기존 Hub Mini에서 ON/OFF·밝기·색 변경을 각 기능별로 학습·재생 시험한다.
5. RF/Bluetooth라면 기존 Hxlight 앱을 유지하고 공식 API 또는 대응 프로토콜이 있는지 판단한다.

원룸이므로 벽 너머 통신 시험은 필수가 아니다. Hub를 커튼 BLE 범위와 IR 가전 시야가 확보되는 위치에 놓고, 가구 가림과 송신 각도를 시험한다. 조명이 RF라면 시야와 무관하게 Hub Mini 학습이 불가능할 수 있다.

| BLE ADV 사용자 통합 | Hxlight 프로토콜 식별·지원 증거 + 적합한 전송 경로 | 연구 후보, 설치만으로 해결된다고 보지 않음 |
| ESP32 기반 중계 | 지원 프로토콜과 전용 프록시 검증 | 추가 장비가 필요한 별도 단계 |
| 교체형 스마트 전구 | 교체 가능한 규격·전압·등기구 조건 확인 | 프로토콜 연구가 길어질 때 비교할 대안 |
| Hxlight 유지 | 위 조건 불충족 | 조명만 기존 앱으로 운영 가능 |

`ha-ble-adv`는 여러 조명 앱 프로토콜을 지원하지만, 확인한 지원 목록에는 Hxlight가 명시돼 있지 않다. 일반 ESPHome Bluetooth proxy와 raw advertising 전송용 proxy도 구분한다. 프로젝트 문서는 직접 어댑터 경로에 비-VM Linux 조건을 제시하므로 현재 VirtualBox에서 바로 된다고 약속하지 않는다.[^bleadv]

초기 타당성 조사는 한 번의 짧은 세션으로 제한한다. 모델·프로토콜 증거가 없으면 색상 자동화 구현을 멈추고 조명을 제외한 나머지 시스템부터 완성한다. 전구 교체나 ESP32 구매는 이번 계획의 기본 전제가 아니다.

## 📦 6. 프로젝터 도입 판단

대상: [프로젝터 구입 링크](https://www.amazon.co.jp/dp/B0F5GQLNWP).

PC Bluetooth 연결 성공은 관찰된 사실이다. 그것이 오디오 출력/입력인지, 입력장치인지, 전용 제어 프로토콜인지는 아직 모른다. Windows의 연결 유형과 프로젝터 설명서에서 확인한다. Bluetooth 연결만으로 화면 전송이나 HA 전원 제어가 된다고 간주하지 않는다.

### 제어 경로 우선순위

1. **기존 SwitchBot IR:** 전원 버튼의 IR 여부부터 확인한다. IR 전원 + Bluetooth 방향키처럼 혼합형일 수도 있다. 정상 종료가 단일 명령인지 확인 창을 거치는지 기록한다.
2. **Android TV Remote:** 본체에 Android TV Remote Service가 있고 Google TV 앱의 리모컨이 실제로 작동하면 HA 공식 통합을 시험한다. ‘Android 탑재’ 광고만으로 지원을 확정하지 않는다.[^androidremote]
3. **ADB:** 공식 Remote Service를 쓸 수 없을 때, 로컬 네트워크 디버깅과 기기 인증이 실제 지원되는지 확인한다. 사용자 승인된 페어링 후 최소 명령만 사용하며 ADB 포트를 인터넷에 노출하지 않는다.[^adb]
4. **HDMI-CEC:** 실제 입력기기·프로젝터·케이블 경로가 모두 지원할 때만 후보로 둔다. Galaxy Book의 HDMI 연결만으로 CEC 제어 가능하다고 가정하지 않는다.

### 기능별 합격 기준

| 기능 | 합격 기준 |
| --- | --- |
| 켜기 | 대기 상태에서 재현 가능; 완전 종료 상태와 구분 |
| 끄기 | 정상 종료·냉각 완료 확인; 토글 재송신 없음 |
| 볼륨·방향키 | 명령별 정확한 반응; 중복 입력 없음 |
| 앱 실행 | 실제 설치 앱에서 확인; 지원하지 않는 앱은 숨김 |
| 상태 표시 | 네트워크 연결·재생 상태·물리 전원을 구분 |

Android TV Remote도 모든 장치에서 종료 후 다시 켜기를 보장하지 않는다. 이 통합의 재생 상태 정보 역시 제한적이다. 필요하면 ‘IR로 기동, 네트워크로 조작’ 조합을 쓴다.[^androidremote]

상태 불명 시 자동 OFF를 보내지 않는다. 기존 assumed-state 가드는 최소 방어로 보존하되, 리모컨·재부팅 후에도 참이라는 보장은 하지 않는다. 프로젝터 전원 강제 차단은 금지한다.

## 🏠 7. SmartThings Station의 역할

우선 기기 밑면과 SmartThings 앱에서 정확한 모델을 확인한다. 삼성 공식 Station 자료는 Matter/Zigbee 호환 기기 연결과 짧게·두 번·길게 누르는 세 가지 루틴을 설명한다. 이 자료만으로 사용자의 ‘Station 2’가 별도 2세대 제품이라고 확정하지 않는다.[^station]

### 도입 순서

1. Station을 SmartThings 앱에 등록한다.
2. SwitchBot 연결 서비스에서 실제로 나타나는 기기를 확인한다.
3. 짧게 누르기 한 가지에만 안전한 동작을 지정해 시험한다.
4. 통과 후 영화 준비·수면 준비·환기 시작을 배치한다. 두 번 누르기의 휴대폰 찾기 설정과 충돌도 확인한다.
5. HA 연동이 필요하면 HA SmartThings 통합에서 버튼 이벤트 또는 사용할 수 있는 가상 기기 상태가 실제 제공되는지 검증한다. 없으면 HA 앱 버튼을 사용한다.[^smartthings]

Station 루틴을 실행하면 임의의 HA script가 자동 호출되는 것은 아니다. 같은 입력이 SmartThings와 HA에서 각각 실행되어 IR이 두 번 나가지 않도록 **한 장면의 실행 주체를 하나로 정한다.**

Station은 HX-light RF/Bluetooth 프로토콜을 범용으로 변환해 주는 장치로 간주하지 않는다. 지원 프로토콜이 확인된 기기에서만 활용한다. SmartThings → SwitchBot 경로는 HA가 꺼져도 가능한 보조 경로지만, 인터넷 장애까지 견디는 로컬 경로인지는 별도로 시험한다.

HA SmartThings 공식 통합 문서에 2026-10 API 정책 변경 주의가 표시되어 있어, 구현일에 실제 계정·지역의 적용 조건을 다시 확인한다. 이번 계획에는 비용이나 지속적인 무료 이용을 확정값으로 넣지 않는다.[^smartthings]

## ⚙️ 8. 실제 집에 맞춘 대시보드·자동화·AI

### 화면 구성안

| 화면 영역 | 내용 |
| --- | --- |
| 상태 | CO₂·온습도·마지막 수신 시각·HA/Hub 가용성 |
| 현재 쓰는 리모컨 | 기존 SwitchBot 패널과 검증된 버튼 |
| 생활 장면 | 검증 완료된 장면만 노출 |
| 설정 | entity 매핑·추정 상태 보정·연결 시험 |

카드에는 전송 중·요청 성공·결과 미확인을 구분한다. `unknown`/`unavailable`을 꺼짐이나 안전한 CO₂ 수치로 바꾸지 않는다. 토글 버튼은 연타·중복 호출을 억제하고 IR 경로 전체에서 2초 간격을 유지한다.

### 장면은 작게 시작한다

| 장면 | 우선 범위 | 확장 조건 |
| --- | --- | --- |
| 영화 준비 | 검증된 커튼 닫기 | 조명·프로젝터 각각 연결 시험 통과 후 추가 |
| 수면 준비 | 커튼·확정 조명 OFF | 안전 종료 확인 후 프로젝터 추가; 선풍기 순환 타이머 제외 |
| 환기 | CO₂ 알림과 사용자의 창문 열기·에어컨 상태 확인 | 에어컨 확정 OFF 확보 전 자동 AC 종료 제외; 선풍기는 수동 |
| 외출 | 재실 정보 안정화 후 커튼·검증된 조명 OFF | 에어컨·선풍기·프로젝터의 상태 불명 토글 제외 |
| 귀가/기상 | 생활 시간·재실 정확도 확인 후 도입 | 냉난방 자동 실행은 마지막 단계 |

조명의 정상 동작이 검증되기 전 영화 모드에서 조명을 껐다고 말하지 않는다. 한 단계 실패 시 나머지를 계속할지 중지할지 장면마다 정하고, 부분 성공을 화면에 표시한다. 프로젝터 기동 실패를 이유로 토글을 반복하지 않는다.

### 환경 알림

기존 1000/1500ppm 안내와 800ppm 미만 10분 환기 완료 정책은 출발점으로 유지한다. 이는 개인 편의 자동화이며 센서 최신성부터 검증한다. 공식 SwitchBot Cloud 문서는 센서 상태 요청 간격을 600초로 설명한다. **센서 자체의 USB 측정 주기와 HA 수신 주기는 다르므로** ‘1분 실시간 감지’라고 표시하면 안 된다.[^switchbot]

센서 신호가 끊기면 환기 완료를 선언하지 않는다. 새 데이터 도착 여부·지연 경고·알림 중복 억제·HA 재시작 후 타이머 정책을 정의한다. SwitchBot 독립 CO₂ 경보는 유지한다. PC 종료 중 HA 알림과 HA 장면은 동작하지 않는다.

### AI 역할과 GitHub 역할

- 단순 제어는 고정 한국어 문장 → 검증된 script로 연결한다.
- 자연어 해석은 지원 기능 목록 안에서만 허용한다. ‘풍량 한 단계’와 ‘강풍’을 같은 명령으로 취급하지 않는다.
- 에어컨의 현재 명령은 ‘전원 버튼 1회’, ‘모드 다음 단계’, ‘종료 예약 다음 단계’다. 확정 ‘꺼줘’, ‘냉방26’, ‘1시간 후 꺼줘’는 현재 자동 실행하지 않는다. 처음에는 에어컨 토글도 AI 노출 없이 수동 버튼만 검증한다.
- 냉방26·난방20·제습·OFF는 검증된 IR 코드 확보 후에만 노출할 수 있는 허용 프리셋이다.
- 센서 값에는 측정값과 수신 시각을 함께 답한다. IR에는 실제 완료를 확인하지 못하면 ‘명령을 보냈다’고 답한다.
- GitHub MCP는 코드·문서 변경 경로다. Git push나 PR 병합이 HA 배포를 의미하지 않는다.
- ChatGPT에서 실시간 HA 제어를 원하면 별도의 인증된 HA 연결이 필요하다. GitHub 연결만으로 집의 실시간 상태나 기기를 제어할 수 있다고 가정하지 않는다.
- 일상 루틴은 HA 내부에서 실행하고 AI에는 필요한 센서와 승인된 스크립트만 노출해 모델 호출과 컨텍스트를 줄인다.

### 추가 구매 판단

- 기존 장비만으로 P0·P1과 일부 알림/장면부터 시작한다.
- Hxlight 통합을 위해 새 하드웨어가 필요하면 프로토콜 지원 근거를 먼저 확보한다.
- 전구 교체 대안은 등기구의 소켓·전압·소비전력 조건이 확인된 뒤 비교한다.
- Galaxy Book을 자주 꺼두거나 외출 시 휴대한다면 기능 확장보다 상시 HA 호스트 확보가 우선이다. 이 경우에만 전용 호스트 이전 비용을 검토한다.

| A13 | 모드·종료 예약 패널의 각 버튼 확인 | ON=모드 순환, OFF=예약 순환; 역매핑 없음 | not-run |

계획 13건: passed 0, failed 0, blocked 1, not-run 12. 테스트 실패가 발견됐다는 집계가 아니다. 실제 스마트폰 접근성·장치 동작 신뢰도는 아직 평가하지 않았다.

기본 장치 명령은 기능별 5회 시험과 실패·지연 기록을 시작 기준으로 한다. 프로젝터 전원은 냉각·재기동 조건에 맞춰 간격을 두며 연속 토글 시험을 하지 않는다. 5회 성공은 장기 신뢰도 보증이 아니다.

> [!note] 다음 에이전트용 요약
> 현행 운영 기준은 실제 HA SwitchBot 패널이다. 전동커튼 3E는 유지. ‘에어컨 수동’의 ON/OFF는 모두 전원 토글. ‘에어컨 off 모드 변경 / on 1시간 切’은 ON=모드 순환, OFF=1~9시간/없음 예약 순환. 확정 에어컨 OFF·26℃ 프리셋을 가정하지 말 것. 현행 코드의 선풍기는 토글/순환이며 allowlist는 15개. Hxlight 앱과 원룸은 사용자 확인, 조명 프로토콜·프로젝터 Bluetooth 제어는 미확정. P0에서 실제 매핑부터 검증한다.
